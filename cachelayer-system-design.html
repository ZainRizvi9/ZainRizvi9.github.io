01. Problem Statement

LLM APIs charge per token. Users frequently submit semantically identical queries with different surface forms, resulting in redundant API calls and unnecessary spend.

THE PROBLEM
Exact match caching fails
"What is the Salesforce implementation timeline?" and "How long does a Salesforce deployment take?" are semantically identical but share no common string. Standard caching misses these.
THE COST
Token spend scales with users, not questions
A 10-person team asking the same questions differently pays 10x what they should. At 10,000 queries/day with 70% paraphrase rate, that's ~$1,000/year in avoidable spend per application.

Why not just use a standard cache?

Redis and Memcached do exact string matching on the cache key. Two queries that mean the same thing but are worded differently produce different hash keys and both result in API calls. The only way to catch paraphrases is to compare meaning, not strings — which requires embedding the query into a vector space where semantic similarity can be measured geometrically.

1
Authentication
Every request must carry a CacheLayer API key (prefix cl_) in the Authorization header. The key is looked up in the users table to retrieve the user_id. All cache operations are scoped to that user_id, ensuring complete isolation between tenants.
2
Query Extraction and Embedding
The last user message is extracted from the messages array as the cache key. It is embedded using all-MiniLM-L6-v2, producing a 384-dimensional L2-normalized vector. Normalization enables dot product to serve as cosine similarity, avoiding the division by magnitude.
3
Similarity Search
The query vector is compared against all cached entries for that user via linear scan. Each entry's stored embedding is deserialized from JSON and scored with a dot product. If any score meets or exceeds the threshold (default 0.80), the cached response is returned immediately.
4
Provider Routing on Cache Miss
On a miss, the model name is checked for "claude" to determine whether to route to Anthropic's /v1/messages endpoint or OpenAI's /v1/chat/completions. Headers are translated appropriately. The upstream API key is passed via X-Upstream-Key, keeping it separate from the CacheLayer key.
5
Cache Write and Response
The response is stored with the query text, embedding, timestamp, and user_id. Stats are updated atomically. The response is returned in standard OpenAI format regardless of provider, with an additional "cached": true field for observability. Token counts are zeroed on cache hits.

03. Core Algorithm

The semantic matching algorithm has three components: embedding, similarity, and threshold selection.

Sentence Embeddings

A sentence embedding maps text to a fixed-length vector where geometric proximity corresponds to semantic similarity. all-MiniLM-L6-v2 was chosen for three reasons: it produces strong semantic similarity scores on standard benchmarks, it runs inference in under 10ms on CPU without a GPU, and its 22M parameter count means it fits in memory alongside the FastAPI server without significant overhead.

Cosine Similarity

src/embedder.py
# Full cosine similarity formula
sim(a, b) = (a · b) / (|a| × |b|)

# After L2 normalization: |a| = |b| = 1, so:
sim(a, b) = a · b   # just a dot product

def embed(text: str) -> np.ndarray:
    return model.encode(text, normalize_embeddings=True)

def similarity(a: np.ndarray, b: np.ndarray) -> float:
    return float(np.dot(a, b))

Why cosine similarity and not Euclidean distance?

Euclidean distance measures the absolute distance between two points in vector space. Cosine similarity measures the angle between them, ignoring magnitude. For sentence embeddings, two queries can have very different magnitudes but nearly identical meaning — cosine similarity handles this correctly. After L2 normalization, cosine similarity reduces to a dot product, which is faster to compute and numerically stable.

Threshold Selection

The threshold τ is the central design parameter. It controls the precision-recall tradeoff:

τ too low → false positives (wrong answers) τ = 0.80 → optimal balance τ too high → false negatives (missed hits)

Empirical testing across 15 paraphrased query pairs showed that hit rate collapses sharply between 0.80 and 0.85, suggesting that paraphrased queries using all-MiniLM-L6-v2 cluster in the 0.80-0.84 cosine similarity range. Below 0.80, topically related but semantically distinct queries begin to score above threshold, risking incorrect cache hits.

Every major technical choice involved a tradeoff. Here is the reasoning behind each one.

API Design: Proxy vs Library

PROXY APPROACH (chosen)
Network-level interception
Zero application code changes. Change one URL and every existing SDK call is cached transparently. Works across languages and frameworks. Can be deployed as shared infrastructure.
LIBRARY APPROACH (rejected)
Import and wrap
Requires code changes in every application. Language-specific. Cannot be shared across teams. GPTCache takes this approach — we explicitly chose not to.

Multi-tenancy: Per-user cache isolation

All cache entries are tagged with a user_id foreign key. Every lookup filters by user_id before computing similarity scores. This ensures that company A's cached responses are never returned to company B, which is a hard requirement for any production deployment handling sensitive data. API keys use the cl_ prefix and are generated with Python's secrets.token_urlsafe(24) for cryptographic randomness.

06. Scale Considerations

The current implementation is optimized for single-application deployments. Here is how it extends to larger scale.

CURRENT · UP TO ~5K ENTRIES
Linear Scan
O(n) similarity search over SQLite. Acceptable latency at small scale. Each entry is deserialized and dot-producted in sequence.
NEXT · 5K–500K ENTRIES
FAISS Index
Approximate nearest neighbor search using Facebook AI Similarity Search. Sub-linear lookup time. Drop-in replacement for the linear scan loop.
PRODUCTION · 500K+ ENTRIES
pgvector + RDS
PostgreSQL with the pgvector extension for native vector similarity. Concurrent writes, horizontal read scaling, managed backups.

Why the current linear scan is acceptable

At 1,000 cached entries, a full linear scan completes in under 2ms on a single core. The dominant latency is the embedding inference at ~8ms, not the search. Linear scan only becomes a bottleneck above ~10,000 entries, which represents months of usage for most single-tenant deployments. FAISS is the clear next step but is not necessary at current scale.

Bottlenecks at scale

EMBEDDING LATENCY
~8ms per query, synchronous
Currently blocks the request thread. At high concurrency, this becomes the primary bottleneck. Fix: asyncio.run_in_executor to move embedding to a thread pool.
SQLite CONCURRENCY
Single writer lock
SQLite allows only one write at a time. Under high concurrent write load (many cache misses simultaneously), writes queue up. Fix: WAL mode or PostgreSQL migration.

07. Future Work

Prioritized by engineering impact and commercial value.

⚡
FAISS approximate nearest neighbor index
Replace the O(n) linear scan with a FAISS IVF index for sub-linear lookup at scale. Maintains the same cosine similarity semantics with dramatically better asymptotic performance above 10,000 cached entries.
📊
Time-series analytics API
Track hit rate, latency, and cost savings at hourly and daily granularity. Expose as a /analytics endpoint so teams can monitor ROI over time rather than just running totals.
🔧
Domain-specific threshold profiles
Let users configure different thresholds per use case. Customer support queries can use 0.75, code generation queries 0.92. Stored per user in the database with a /config endpoint.
🛡️
Semantic coherence validation
Score the semantic similarity between a query and its proposed cached response before returning it. Reject cache entries where the query-response similarity falls below a coherence threshold, preventing poisoned cache responses.
🔔
Cache miss webhooks
Let users register a webhook URL that is called on every cache miss with the query and response. Enables downstream systems to proactively seed the cache with expected future queries before traffic arrives.
